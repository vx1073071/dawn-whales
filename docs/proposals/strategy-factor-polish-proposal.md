## 一、因子层打磨 (7 项建议)

### 1.1 🔴 P0 — 数据预处理管线 (Factor Preprocessing Pipeline)

**问题**: 现有因子引擎直接消费原始数据，无任何预处理步骤。Alpha 因子效果被行业和市值偏差严重污染【研究验证：不做行业中性化的低PE选股，结果全是银行股】。

**建议**: 新建 `electron/engine/factors/factor-preprocessor.ts`

```
Preprocessing Pipeline (每因子必经):

Step 1: MAD 去极值
  median ± 3 × 1.4826 × MAD  → clip extreme values
  (MAD 比 3σ 更稳健, 不受极端值影响)

Step 2: 行业中性化 (必做)
  因子值 = 因子-均值(行业) / 标准差(行业) × 目标标准差 + 目标均值

Step 3: 市值中性化 (可选, 大/小盘因子跳过)
  对 log(市值) 回归取残差

Step 4: Z-score 标准化
  (x - μ) / σ  → 不同因子间可比

Step 5: 缺省值填充
  行业均值/中位数  → 避免因缺值排除样本
```

**人类使用习惯对齐**: 散户投资者不知道「中性化」是什么意思，但他们知道「为什么全是银行股」😰。预处理应该**静默运行**但**可展开查看** — 用户点击「为什么选这些股票」时展示处理过程。

### 1.5 🟢 P2 — 因子拥挤度报警 (Factor Crowding Alert)

**问题**: 当太多资金押注同一因子时，因子会失效（拥挤崩溃）。2024 年小市值因子拥挤度飙升至 90% percentile 后剧烈回撤。

**建议**: 新增 `factor-crowding-monitor.ts`，计算：
- **估值溢价**: 高因子暴露组的 P/E 相对全市场溢价
- **持仓集中度**: 公募基金重仓股在因子高分组的重叠率
- **因子换手率**: 高分组的成分股替换频率
- **Alpha 衰减速度**: IC 半衰期趋势

阈值：拥挤度 > 80% → 🟡 预警，> 95% → 🔴 危险

### 1.7 🟡 P1 — 因子回测 (单因子测试)

## 四、数据流 & 架构打磨 (5 项建议)

### 4.1 🔴 P0 — 因子数据统一层 (Factor Data Adapter)

**问题**: `multi-factor.ts` 依赖 5 个独立数据模块（SentimentIndexEngine / CapitalFlowRank / DragonTigerList / FundHoldings / StockDiagnosis），数据格式各异，难以扩展。

**建议**: 新增 `electron/engine/factors/factor-data-adapter.ts` — 统一的因子数据接口层：

```typescript
interface FactorDataProvider {
  getFactorValues(symbols: string[], factorIds: string[], dateRange: DateRange): Promise<FactorMatrix>;
  getLatestValues(symbols: string[], factorIds: string[]): Promise<FactorMatrix>;
  subscribe(symbols: string[], factorIds: string[], callback: FactorUpdateCallback): void;
}

// FactorMatrix = symbols × factors × dates
// 所有因子引擎都通过此层消费数据
```

这样新增因子类型（比如从富途API获取实时数据）只需要实现新的 Provider 并注册到适配器。

---

### 4.2 🟡 P1 — 策略运行日志标准化

**问题**: 不同策略引擎使用不同的 `log.info()`，无统一日志格式，排查问题困难。

**建议**: 建立策略日志标准：

```typescript
interface StrategyLogEntry {
  timestamp: string;
  strategyId: string;
  level: 'signal' | 'order' | 'error' | 'lifecycle' | 'perf';
  event: string;          // e.g. 'signal:buy', 'order:filled', 'lifecycle:start'
  data: Record<string, unknown>;
  contextId: string;      // unique per run session
}
```

所有策略引擎日志写入统一格式，后端可按 `contextId` 串联整个决策链条。

---

### 4.3 🟡 P1 — 策略回测缓存

**问题**: 用户反复回测相同参数，每次都重新计算。`strategy-engine.ts` 有 30s 缓存但仅限 K 线数据。

**建议**: 建立**回测结果缓存**：
- 缓存键: `strategyId + paramHash + symbol + dateRange`
- 缓存过期: 24 小时（或数据源更新时失效）
- 存储: SQLite `backtest_cache` 表

用户改一个参数后，只重新计算变化的部分，未变的因子数据直接复用。

---

### 4.4 🟢 P2 — 清除 @ts-nocheck 污染

**需清理的 4 个文件**:
1. `strategy-optimizer.ts` (27KB) — 最大的 @ts-nocheck
2. `strategy-ranking-engine.ts` (41KB) — EventEmitter polyfill 冲突
3. `strategy-export-import.ts` (26KB) — EventEmitter polyfill 冲突
4. `strategy-runner.ts` (37KB) — 类型声明不完整

**方案**: 统一使用 `import { EventEmitter } from 'events'` + `vitest.config.ts` 别名（已有的 `events-polyfill.ts` 方案），移除 4 个文件中的重复 polyfill + @ts-nocheck。
