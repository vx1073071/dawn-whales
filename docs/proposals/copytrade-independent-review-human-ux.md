## 一、🔴 致命问题

### 1.1 信号来源不透明 — 用户不知道为什么会跟单

**现状**: 信号从服务器推送(`GET /api/signal/pending`)，用户看到一条"买入 BTCUSDT"的跟单指令。

**人类问题**: 用户不知道:
- 这个信号是谁发的？(哪个信号提供者)
- 信号提供者的历史业绩如何？(胜率/回撤/夏普)
- 信号的置信度是多少？
- 信号是基于什么逻辑生成的？

**建议**: 每条信号必须包含:
- 信号提供者 ID + 昵称
- 30日胜率 + 总收益 + 夏普比率
- 信号置信度 (0-100%)
- 策略简述 (如 "BTC 5分钟 MACD金叉")

### 1.2 跟单金额无智能建议

**现状**: 信号包含 `qty` 字段，直接执行。

**人类问题**: 用户资金 5000 USDT，信号要求买 2 BTC (184,000 USDT)。直接失败。

**建议**: 跟单引擎执行前检查:
1. 用户可用余额 ≥ 信号金额
2. 建议跟单比例 = min(信号金额/余额, 用户预设最大百分比)
3. 提示: "信号要求 0.1 BTC ($9,200)，您的可用余额 $5,000，建议跟单 $500 (5.4%)"

### 1.3 死信队列无人类可操作界面

**现状**: `deadLetter` 仅存储，无前端展示。

**人类问题**: 3 次失败后信号进入死信，用户完全不知道。可能是:临时网络故障 / API Key过期 / 余额不足 / 券商不支持该标的。

**建议**: 死信队列前端面板:
- 分类: "网络故障" / "余额不足" / "API密钥过期" / "标的不支持"
- 操作: 重试 / 忽略 / 调整参数后重试
- 提醒: 死信超过 10 条 → 全局通知

## 二、🟡 功能缺失

### 2.1 跟单无"模拟模式"

**现状**: 所有跟单直接开真实仓位。

**人类问题**: 用户不敢开启跟单，怕亏钱。没有模拟/回测模式让用户先看效果。

**建议**:
- 模拟模式: 信号→模拟下单→记录虚拟 PnL→展示 (不实盘)
- 运行 7 天后用户看到模拟 PnL → 一键切换真实模式
- 类似 eToro 的 "Demo Account" 概念

### 2.2 跟单无"暂停规则"

**现状**: 跟单要么全开，要么全关。

**人类问题**: 
- "BTC 跌破 80000 我就不跟了" → 无法设置
- "今天已经亏了 500 刀，剩下的信号不跟了" → 无法设置
- "这个信号提供者连亏 3 笔了，暂停他" → 无法设置

**建议**: 跟单暂停规则:
- 条件 A: 单日亏损 ≥ $X → 暂停所有跟单
- 条件 B: 信号提供者连续亏损 ≥ N 笔 → 暂停该提供者
- 条件 C: 标的跌破/涨破 Y 价格 → 暂停该标的跟单
- 条件 D: 市场休市 → 暂停该市场跟单

### 2.3 无分润透明度

**现状**: 分润比例在代码中，用户看不到。

**人类问题**: 用户不知道每笔跟单要分多少钱给信号提供者。

**建议**: 
- 下单确认弹窗显示: "信号提供者分润: 15% (预计 $xx.xx)"
- 交易历史中显示每笔分润明细
- 月度分润汇总: "本月共跟单 xx 笔，分润总计 $xxx"

### 2.4 通知过度或不足

**现状**: 每条跟单都通知，噪音大。

**人类问题**: 一天 200 条信号 → 200 条通知 → 用户关闭通知权限 → 真正重要的通知看不到。

**建议**: 
- 仅通知异常: 跟单失败/死信/异常大单 (>用户资产 10%)
- 摘要通知: "今天 15 条跟单，13 成功 2 失败，总 PnL +$230"
- 用户可调节通知频率: 每条/摘要/仅异常

## 三、🟢 人类UX打磨

### 3.1 🔥 OpenD 离线体验 (人类最常遇到)

**用户场景**: 白天在公司用桌面端 (OpenD在线) → 晚上回家合上电脑 (OpenD离线) → 服务器继续推信号 → 次日打开电脑 → ?

**期望行为**:
1. 打开电脑 → 看到 "昨晚有 8 条信号待处理"
2. 一键 "全部执行" 或 "逐条审核"
3. 处理完成 → "8 条已全部执行"

**当前**: 离线队列存在但前端无对应 UI。用户打开电脑看不到待处理信号。

### 3.2 🔥 跟单仪表盘应该是一块"驾驶舱"

**用户期望**: 打开跟单页面，一眼看到:
- 中央: 今日 PnL 大数字 (绿/红)
- 左侧: 各券商仓位分布饼图
- 右侧: 最近 10 条跟单时间线
- 顶部: 服务器连接状态 + OpenD 状态
- 底部: 各信号提供者业绩排名

**当前**: 组件分散在不同页面，需要来回切换。

### 3.3 信号提供者应该是"关注"而非"订阅"

**人类心智模型**: Twitter/YouTube 的 "关注" → 内容自动流入

**当前**: 技术术语 "跟单设置" 不够直观

**建议**:
- "发现信号提供者" → 排行榜/推荐
- "关注" → 一键开始跟单 (默认模拟模式)
- "已关注" → 显示近期信号 // 盈亏 // 设置

### 3.4 分润应该是"双方可见"

**人类心智模型**: Uber 司机和乘客都看到价格

**当前**: 分润仅服务端计算，用户看不到

**建议**:
- 信号提供者端: "你的信号被跟单 xx 次，累计分润 $xxx"
- 跟单者端: "本笔跟单分润 $x.xx 给 [提供者名称]"

## 四、安全风险

### 4.1 API Key 解密时机

**现状**: 收到信号时解密 API Key → 下单

**风险**: 解密后的 Key 在内存中持续存在直到下单完成。如果服务器被入侵，所有 15 家券商 API Key 同时暴露。

**建议**: 
- Key 使用后立即从内存清零
- 单次下单超时 30s → 自动断开 + 清除 Key
- 审计日志: 每次解密记录 (不含 Key 明文)

### 4.2 无每日跟单限额

**人类问题**: 信号提供者被黑 → 发出 1000 条 "买入" 信号 → 用户账户被掏空。

**建议**:
- 每日跟单次数上限 (默认 50)
- 每日跟单金额上限 (默认 $10,000)
- 超过上限 → 暂停 + 通知用户确认
- 用户可调节上限

## 五、架构打磨建议

### 5.1 信号优先级过于简单

**现状**: P0/P1/P2 三级优先级

**建议增加维度**:
- 信号提供者信誉 (高信誉 → 提升优先级)
- 用户持仓相关 (已持仓标的 → 优先级+)
- 市场状态 (休市 → 自动降级)

### 5.2 无跨券商智能路由

**现状**: 信号指定 targetBrokers，直接分发

**建议**: 
- 自动检查哪个券商手续费最低 → 优先路由
- 自动检查哪个券商余额足够 → 排除不够的
- 自动检查哪个券商支持该市场/标的 → 排除不支持的
- 例如: 信号 "买入 AAPL" → 自动选 Schwab (免佣) 而非 Tiger (收费)

## 七、给 PM 的建议

1. **P0 安全立即修 (7h)**: 限额 + Key即焚 + 金额检查 — 这是钱的安全，不是功能
2. **P1 核心体验 (21h)**: 信号透明+模拟+暂停+死信+离线待处理 — 让用户敢用、能用
3. **P2 打磨 (15h)**: 驾驶舱+分润+通知+路由 — 从能用到好用
4. **核心理念**: 跟单不是自动执行器，是用户的 AI 交易助手。用户需要: 知道谁在帮ta交易 + 能暂停/限额/模拟 + 钱是安全的。
