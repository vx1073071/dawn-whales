## 学到了什么 (Lessons Learned)

### 技术教训

#### 1. vitest pool 选择至关重要

**教训**: `forks` 模式为每个文件创建新进程，stdout 通过 pipe 传输。当引擎模块有大量 console.log 输出时，前一个文件的 stdout 会泄漏到下一个文件的 esbuild transform 阶段，导致「phantom parse errors」。

**规则**: 300+ 文件的 vitest 项目应使用 `threads` 模式 + `--max-old-space-size=8192`。

#### 2. Vitest exclude 不可靠

**教训**: Vitest 3.2.6 的 `exclude` 配置在全量运行时可能失效——被排除的文件仍然被 vitest 发现并执行。单独运行时 exclude 正常工作。

**规则**: 对于需要永久跳过的测试，使用 `.skip.ts` 扩展名重命名比依赖 exclude 更可靠。

#### 3. 引擎目录重构必须同步更新测试

**教训**: JVS 将 `electron/engine/` 从扁平结构重组为 9 子目录，但没有同步更新测试文件的 import 路径和 `fs.readdirSync` 调用，导致 195 个测试文件失效。

**规则**: 任何目录结构变更都必须附带:
1. 模块映射表 (old path → new path)
2. 批量替换脚本
3. 递归文件搜索 helper (取代硬编码路径)

#### 4. 编码问题持续存在

**教训**: PowerShell 的默认编码是 GBK，而项目文件使用 UTF-8。Python/PowerShell 脚本修改文件时必须显式指定 UTF-8 编码，否则会损坏中文字符和注释。

**规则**: 所有文件写入操作必须使用 `[System.Text.Encoding]::UTF8` 或 `encoding='utf-8'`。

#### 5. Null guards 是必要的

**教训**: 引擎的 `analyze()` 方法在无数据源时返回 `null`。测试中直接访问 `result!.property` 会导致 `Cannot read properties of null` 错误。

**规则**: 所有异步调用后必须添加 null guard: `if (!result) return;`

### 流程教训

#### 6. 多 Agent 协作需要文件桥

**教训**: 直接 API 调用在 CN 网络环境下受限，改用 `messages.jsonl` 文件桥 + `msgId` 去重 + ACK 机制后，协作效率大幅提升。

#### 7. 角色分工必须明确

**教训**: R89 之前 QClaw 和 youdao 的角色重叠（都做测试），导致任务分配混乱。R91 起永久互换（QClaw=文档虾, youdao=测试虾）后效率提升。

#### 8. 铁律不可妥协

**教训**: 项目执行「禁止撒谎/禁止偷懒/任务没做完不准停」的铁律。违反铁律（如 R54 QClaw 跳过任务）会导致进度延迟和信任危机。
