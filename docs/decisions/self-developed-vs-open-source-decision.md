## 决策概述

### 背景

DAWN WHALES v1.2.0 需要实现 AI 协作功能，通过多个 AI Agent 协作分析，帮助创作者生成高质量交易策略。

### 可选方案

1. **自研 (TypeScript)** - 完全自研，TypeScript 原生集成
2. **TradingAgents (Python)** - 使用开源 TradingAgents 框架
3. **Python 微服务** - Python 微服务 + HTTP API
4. **LangGraph** - 使用 LangGraph Agent 框架

### 最终决策

**选择方案 1: 自研 (TypeScript)**

## 为什么不用 TradingAgents

### TradingAgents 简介

- **项目**: https://github.com/TauricResearch/TradingAgents
- **Stars**: 9K+
- **协议**: Apache-2.0
- **语言**: Python
- **特性**: 多 Agent 协作、辩论机制、决策记忆

### 不采用的原因

#### 1. Apache-2.0 协议限制

**问题**:
- Apache-2.0 要求保留版权声明
- 修改需要标注
- 商业化需要遵守协议条款

**影响**:
- 增加合规成本
- 限制商业化灵活性
- 潜在法律风险

**对比**:
- 自研: 0 协议依赖，完全自主
- TradingAgents: Apache-2.0，有限制

#### 2. Python 语言不匹配

**问题**:
- DAWN WHALES 是 TypeScript/Electron 项目
- TradingAgents 是 Python 项目
- 需要进程间通信 (IPC)

**影响**:
- 增加部署复杂度
- 增加性能开销
- 增加维护成本

**对比**:
- 自研: TypeScript 原生，无缝集成
- TradingAgents: Python，需要 IPC

#### 3. 定制性受限

**问题**:
- TradingAgents 是通用框架
- 需要深度定制才能满足需求
- 定制需要修改源码

**影响**:
- 定制成本高
- 升级困难
- 维护成本高

**对比**:
- 自研: 完全定制，灵活调整
- TradingAgents: 有限定制，升级困难

### 结论

虽然 TradingAgents 是优秀的开源项目，但在协议依赖、语言集成、定制性等方面不符合 DAWN WHALES 的需求，因此不采用。

## 为什么不用 Python 微服务

### 方案概述

- **架构**: Python 微服务 + HTTP API
- **语言**: Python
- **通信**: HTTP/REST

### 不采用的原因

#### 1. 性能开销

**问题**:
- HTTP 请求有网络开销
- JSON 序列化/反序列化有开销
- 进程间通信有开销

**影响**:
- 响应时间增加 100-500ms
- 吞吐量降低
- 资源消耗增加

**对比**:
- 自研: 进程内调用，几乎无开销
- Python 微服务: HTTP 调用，有开销

#### 2. 部署复杂度

**问题**:
- 需要部署 Python 环境
- 需要部署 Python 微服务
- 需要管理两个服务

**影响**:
- 部署复杂度增加
- 运维成本增加
- 故障点增加

**对比**:
- 自研: 单一 Electron 应用，部署简单
- Python 微服务: 两个服务，部署复杂

#### 3. 用户体验

**问题**:
- 需要启动 Python 微服务
- 需要配置 Python 环境
- 可能出现兼容性问题

**影响**:
- 用户体验差
- 技术支持成本高
- 用户流失风险

**对比**:
- 自研: 开箱即用，体验好
- Python 微服务: 需要配置，体验差

### 结论

Python 微服务方案在性能、部署、用户体验等方面都不如自研方案，因此不采用。

## 为什么不用 LangGraph

### LangGraph 简介

- **项目**: https://github.com/langchain-ai/langgraph
- **Stars**: 5K+
- **协议**: MIT
- **语言**: Python
- **特性**: Agent 编排、状态管理、工具调用

### 不采用的原因

#### 1. MIT 协议限制

**问题**:
- MIT 协议要求保留版权声明
- 虽然限制少，但仍有合规成本

**影响**:
- 需要保留版权声明
- 需要遵守协议条款

**对比**:
- 自研: 0 协议依赖
- LangGraph: MIT 协议

#### 2. Python 语言不匹配

**问题**:
- 与 TradingAgents 相同的问题
- 需要进程间通信
- 性能开销

**对比**:
- 自研: TypeScript 原生
- LangGraph: Python

#### 3. 依赖重

**问题**:
- LangGraph 依赖 LangChain
- LangChain 依赖众多
- 依赖树庞大

**影响**:
- 包体积大
- 安装时间长
- 依赖冲突风险

**对比**:
- 自研: 无依赖，轻量级
- LangGraph: 依赖重，体积大

#### 4. 定制性受限

**问题**:
- LangGraph 是通用框架
- 需要深度定制
- 定制需要修改源码

**对比**:
- 自研: 完全定制
- LangGraph: 有限定制

### 结论

LangGraph 在协议、语言、依赖、定制性等方面都不如自研方案，因此不采用。

## 0 协议依赖的好处

### 1. 完全自主

**好处**:

- 可自由修改、分发、商业化
- 无合规成本

**对比**:
- Apache-2.0: 需要保留版权声明，修改需要标注
- MIT: 需要保留版权声明
- 自研: 完全自主

### 2. 商业化灵活

**好处**:
- 可自由选择商业模式
- 可自由定价
- 可自由选择分发方式

**对比**:
- 开源协议: 可能限制商业化
- 自研: 完全灵活

### 3. 无法律风险

**好处**:
- 无协议违规风险
- 无版权纠纷风险
- 无合规审计成本

**对比**:
- 开源协议: 有合规风险
- 自研: 无风险

### 4. 长期维护

**好处**:
- 不受上游项目影响
- 可自主决定升级策略
- 可自主决定功能方向

**对比**:
- 开源项目: 受上游影响
- 自研: 完全自主

## 自研的成本与收益

### 成本

#### 1. 开发成本

**估算**:
- 架构设计: 2 周
- 核心开发: 4 周
- 测试调试: 2 周
- 文档编写: 1 周
- **总计**: 9 周 ≈ 2.25 个月

**成本**:
- 开发人员: 1 人
- 月薪: 30,000 元
- 总成本: 30,000 × 2.25 = **67,500 元**

#### 2. 维护成本

**估算**:
- 每月维护: 1 周
- 年维护成本: 30,000 × 12 = **360,000 元/年**

### 收益

#### 1. 商业化收益

**估算**:
- 单次分析成本: 0.016 USDT ≈ 0.12 元
- 单次分析售价: 2.0 USDT ≈ 14.4 元
- 毛利: 14.28 元 (99.2%)

**月收入预估** (1000 用户，每人每月 100 次):
- 收入: 1000 × 100 × 14.4 = 1,440,000 元
- 成本: 1000 × 100 × 0.12 = 12,000 元
- 毛利: 1,428,000 元

#### 2. 回收周期

**估算**:
- 开发成本: 67,500 元
- 月毛利: 1,428,000 元
- 回收周期: 67,500 / 1,428,000 ≈ **0.05 个月 ≈ 1.5 天**

**结论**: 自研成本在 1.5 天内即可回收，ROI 极高。
