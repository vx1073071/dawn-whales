## 2. 单只虾资源消耗模型

### 2.1 虾的工作负载分析

虾（AI Agent）在本地执行的操作可分为三类：

| 工作类型 | CPU占用 | 内存占用 | 持续时间 | 频率 |
|---------|---------|---------|---------|------|
| **代码编写** | 低 (<5%) | ~200MB | 持续 | 高频 |
| **文件IO** | 低 (<10%) | ~100MB | 瞬间 | 高频 |
| **Git操作** | 低-中 (10-30%) | ~150MB | 1-3秒 | 中频 |
| **TypeScript编译** | **高 (50-100%单核)** | ~500MB | 5-30秒 | 中频 |
| **Vite构建** | **高 (多核利用)** | ~800MB | 10-60秒 | 低频 |
| **Vitest测试** | **高 (多核利用)** | ~600MB | 10-120秒 | 中频 |
| **npm install** | 低 | ~200MB | 30-300秒 | 极低 |

### 2.2 峰值负载模型

当多只虾同时工作时，资源消耗不是简单的线性叠加，因为：

1. **编译/测试可并行**: tsc 和 vitest 都能利用多核心
2. **代码编写是串行的**: 一个虾在写文件时，其他虾可以并行编译
3. **Git操作有锁**: git commit 是原子操作，多个虾同时commit会串行

**峰值负载估算**（N只虾同时编译/测试）：

```
CPU核心需求 = N × 1.5 (平均值，考虑编译和测试交替)
内存需求 = N × 400MB + 2GB (系统开销)
磁盘IO = N × 并发文件操作 (SSD可承受)
```

## 3. 不同虾数量的资源占用预测

### 3.1 理论计算

| 虾数量 | CPU核心需求 | CPU占用% | 内存需求 | 内存占用% | 瓶颈 |
|--------|------------|---------|---------|----------|------|
| 4 | 6 核 | 25% | 3.6 GB | 6% | 无 |
| 6 | 9 核 | 38% | 4.4 GB | 7% | 无 |
| **8** | **12 核** | **50%** | **5.2 GB** | **8%** | **无** |
| 10 | 15 核 | 63% | 6.0 GB | 9% | 轻微 |
| 12 | 18 核 | 75% | 6.8 GB | 11% | CPU |
| 16 | 24 核 | 100% | 8.4 GB | 13% | CPU满载 |
| 20 | 30 核 | 125% | 10.0 GB | 16% | CPU严重超载 |
| 24 | 36 核 | 150% | 11.6 GB | 18% | 不可行 |

### 3.2 关键发现

**内存完全不是瓶颈**: 64GB内存可以支持超过100只虾同时运行。实际限制因素是CPU和软件架构。

**CPU是主要瓶颈**: 
- 8只虾：CPU仅占用50%，还有大量余量
- 12只虾：CPU占用75%，接近满载
- 16只虾：CPU占用100%，编译会开始排队

**软件瓶颈比硬件更严重**:

```
硬件上限: 16只 (CPU满载)
     │
     ▼ 但软件瓶颈更早出现:
     │
     ├── Git锁: 8只同时commit时排队明显
     ├── 单仓库冲突: 超过8只时文件修改冲突概率陡增
     ├── Chat-bridge消息队列: 理论上无上限，但消息量大会影响可读性
     └── PM协调复杂度: 超过10只时PM难以有效协调
     │
     ▼
实际建议上限: 8-10只
```

## 4. 软件瓶颈详细分析

### 4.1 Git锁竞争

Git 的 `.git/index.lock` 机制意味着：**同时只能有一只虾执行 write 操作**。

```
场景: 8只虾同时完成编码，都要commit

时间线:
t=0s  虾1 开始 commit  ▓░░░░░░░
t=1s  虾2 等待锁       ░▓░░░░░░
t=2s  虾3 等待锁       ░░▓░░░░░
t=3s  虾4 等待锁       ░░░▓░░░░
t=4s  虾5 等待锁       ░░░░▓░░░
t=5s  虾6 等待锁       ░░░░░▓░░
t=6s  虾7 等待锁       ░░░░░░▓░
t=7s  虾8 等待锁       ░░░░░░░▓

总耗时: ~8秒 (串行)
     vs
理想并行: ~1秒 (如果无锁)

结论: 8只虾commit时，每只平均等待3.5秒。可以接受。
     16只虾commit时，每只平均等待7.5秒。明显卡顿。
```

### 4.2 单仓库文件冲突

当前架构下所有虾共享一个 git 仓库。当多只虾同时修改同一文件时：

| 虾数量 | 冲突概率/轮 | 解决耗时 |
|--------|------------|---------|
| 4 | ~5% | ~2分钟 |
| 6 | ~15% | ~5分钟 |
| 8 | ~25% | ~8分钟 |
| 10 | ~40% | ~12分钟 |
| 12 | ~55% | ~15分钟 |

**这是8虾架构要解决的核心问题** — 通过目录隔离将冲突概率降至 ~5%。

### 4.3 磁盘IO压力

现代NVMe SSD的顺序读写可达 3000-7000 MB/s，随机读写 300-700K IOPS。

8只虾同时编译时的IO：
- tsc 读取类型定义: ~50MB × 8 = 400MB/s
- Vite 写入构建产物: ~100MB × 8 = 800MB/s
- **总计: ~1.2GB/s** — NVMe SSD 完全无压力

16只虾同时编译时的IO：
- **总计: ~2.4GB/s** — 高端NVMe仍无压力，但中低端SSD可能饱和

**结论: SSD不是瓶颈（除非是非常入门的SSD）。**

## 5. 分阶段建议

### 5.1 推荐方案: 分三阶段扩展

基于你的顶级配置，建议分阶段增加虾数量：

#### 阶段一: 验证期 (R33-R35, 3轮)

| 项目 | 配置 |
|------|------|
| **虾数量** | **8只** |
| 架构 | 分层并行（数据/券商/引擎/UI/基础设施） |
| 目标 | 验证契约先行 + 目录隔离 + 测试分片 |
| 预期产出 | ~5000L/轮, +200 tests/轮 |
| CPU占用 | 50% (余量充足) |
| 风险 | 低 |

**为什么先8只**: 
- 8只是软件架构的"甜点区" — 冲突可控、协调可行
- 同时能充分利用你50%的CPU，不浪费资源
- 为下一阶段扩展积累经验

#### 阶段二: 扩展期 (R36-R40, 5轮)

| 项目 | 配置 |
|------|------|
| **虾数量** | **10只** (+2只专项虾) |
| 新增 | 性能优化虾 + 文档虾 |
| 目标 | 在8只稳定基础上，增加专项能力 |
| 预期产出 | ~6500L/轮, +280 tests/轮 |
| CPU占用 | 63% |
| 风险 | 中低 |

**10只分工**:
- 数据层: 2只 (行情 + 账户)
- 券商层: 1只
- 引擎层: 4只 (策略 + 风控 + 执行 + 自动化)
- UI层: 2只 (交易 + 系统)
- 专项: 2只 (性能优化 + 文档)
- 基础设施: 3只共享 (PM + QA + CI)

#### 阶段三: 极限期 (R41+, 可选)

| 项目 | 配置 |
|------|------|
| **虾数量** | **12只** |
| 条件 | 前两个阶段运行稳定，冲突率 < 10% |
| 目标 | 榨干CPU，最大化产出 |
| 预期产出 | ~7500L/轮, +350 tests/轮 |
| CPU占用 | 75% |
| 风险 | 中等（编译排队，PM协调压力大） |

**为什么不推荐16只**:
- CPU满载时，编译排队导致每只虾的"感知延迟"增加
- git锁竞争严重，commit平均等待7.5秒
- PM协调16只虾的复杂度极高，容易失控
- 边际收益递减：12→16只，产出只增加15%，但复杂度翻倍

## 6. 特殊场景分析

### 6.1 全量测试时

当QA虾执行 `npm run test:full` 时：
- 会占用全部24核心（vitest并行跑所有测试）
- 此时其他虾如果也在编译，会争夺CPU
- **建议**: 全量测试时，其他虾暂停编译，专注代码编写（低CPU）

### 6.2 Electron打包时

`npm run dist:win` 打包Electron应用：
- 占用4-8核心，持续2-5分钟
- 内存占用突增至 2-3GB
- **建议**: 打包由CI虾在后台执行，不影响工作虾

### 6.3 npm install时

多虾同时运行 `npm install`：
- 网络带宽可能成为瓶颈（如果依赖包大）
- 磁盘IO高（解压大量文件）
- **建议**: 统一由CI虾管理依赖，其他虾不单独install

```
      即使未来扩展到10-12只，也完全在承受范围内。
```

## 8. 最终建议

### 8.1 虾数量建议表

| 场景 | 推荐虾数 | 理由 |
|------|---------|------|
| **立即实施** | **8只** | 硬件轻松支持，软件架构验证 |
| **3轮后扩展** | **10只** | 增加性能优化 + 文档专项虾 |
| **极限尝试** | **12只** | 硬件仍可承受，但协调成本高 |
| **不推荐** | 16+ | CPU满载，git锁严重，边际收益低 |

### 8.2 配置利用率

| 虾数 | CPU利用率 | 内存利用率 | 配置评价 |
|------|----------|-----------|---------|
| 8 | 50% | 8% | 轻松驾驭，游刃有余 |
| 10 | 63% | 9% | 良好利用，仍有余量 |
| 12 | 75% | 11% | 接近满载，需要优化 |
| 16 | 100% | 13% | 超载运行，体验下降 |

### 8.3 一句话总结

> **你的电脑配置（Ultra 9 275HX + 64GB）可以轻松支持8只虾并行，有余量扩展到10-12只。软件架构（git锁、单仓库冲突）是实际瓶颈，不是硬件。**
