## 2. 安全特性逐项审计

### 2.1 原子扣费

**机制**:
```
deduct(userId, amount, reason, tradeId):
  1. check balance >= amount  ← 余额检查
  2. if insufficient → throw PointsInsufficientError
  3. balance -= amount        ← 修改余额
  4. ledger.push({...})       ← 写入账单
  5. return { success, newBalance }
```

**验证方法**:
- 源码：`usdt-points-manager.ts` `deduct()` 方法为同步操作，无 yield/await 断点
- 测试：并发扣费 2 笔同时 → 余额正确 (youdao Q-01 用例)

**审计结论**: ✅ 通过。`deduct()` 从余额检查到减扣到记账是单一同步调用，无并发竞态窗口。

### 2.2 操作幂等

**机制**:
```ts
// reconciliation-engine.ts
checkAndMarkTradeId(tradeId):
  if processedTradeIds.has(tradeId) → { idempotent: true, processed: false }
  else → processedTradeIds.add(tradeId) → { idempotent: false, processed: true }
```

**验证方法**:
- 源码：`Set<string>` 去重存储，O(1) 查找
- 测试：提交同一 tradeId 两次 → 第二次返回 idempotent=true (JVS J-01 用例)

**审计结论**: ✅ 通过。防重放机制正确，同一 tradeId 多次提交只处理一次。

### 2.3 总量守恒

**机制**:
```ts
// reconciliation-engine.ts
verifyConservation():
  supply = sum of all initial deposits (charge entries)
  balanceSum = sum of all current balances
  feeSum = sum of all fees collected (trade_fee + p2p_fee + withdraw)
  expected = supply - feeSum  // fees transfer, not destroy
  actual = balanceSum
  pass = |expected - actual| ≤ 0.0001
```

**验证方法**:
- 源码：遍历全量 ledger 重建预期余额，逐项对账
- 测试：模拟用户充值→交易→扣费流程后，验证 `expected ≈ actual` (JVS J-01 用例)

**审计结论**: ✅ 通过。总量守恒验证算法正确，精度阈值 0.0001 合理（6 位小数舍入误差）。

### 2.4 汇率异常检测

**机制**:
```ts
detectRateAnomaly(currency, currentRate):
  if changePercent > 5% → reject (valid: false)
  else → accept + update history
```

**降级链**: CoinGecko → Binance → static (2026-06 人工维护)

**验证方法**:
- 源码：`RATE_SPIKE_THRESHOLD = 5`，历史汇率存储 + 对比
- 测试：模拟汇率突然跳变 10% → 返回 `valid: false` (youdao Q-01 用例)

**审计结论**: ✅ 通过。5% 阈值合理（正常汇市单日波动通常 < 3%），降级链覆盖了 API 不可用和汇率异常两种场景。

### 2.5 账实核对

**机制**:
```ts
reconcile():
  1. 从 ledger 重建所有用户余额
  2. 对每个用户: ledgerBalance vs actualBalance
  3. diff > 0.0001 → alert
  4. 全局: expectedSupply vs totalSupply → alert
```

**验证方法**:
- 源码：`ledger → userBalanceMap → 逐用户对比`
- 测试：构造 ledger 与实际余额不一致的场景 → 触发告警 (JVS J-01 用例)

**审计结论**: ✅ 通过。账实核对算法完整，单用户+全局双维度覆盖。

### 2.6 死信降级

**机制**:
```ts
onTradeComplete(trade):
  retry loop (max 3):
    1. calc fee
    2. deduct fee
    if PointsInsufficientError → dead letter (non-retryable)
    if other error → retry (100ms/200ms/400ms)
  if all retries exhausted → dead letter
```

**验证方法**:
- 源码：`MAX_RETRIES = 3`，`RETRY_DELAYS = [100, 200, 400]`，`PointsInsufficientError` 不重试
- 测试：余额不足 → 立即死信 / 汇率过期 → 3 次重试后死信 (youdao Q-01 用例)

**审计结论**: ✅ 通过。死信机制正确区分可重试和不可重试错误，不阻塞交易主流程。

## 7. 审计结论

### 7.1 总体评价

v1.12.0 USDT 积分系统 **安全性通过审计**。所有 6 项关键安全特性（原子扣费、操作幂等、总量守恒、汇率异常检测、账实核对、死信降级）均已实现并通过验证。

### 7.2 优点

1. **积分与资金隔离**: 积分系统独立于用户券商账户，设计安全
2. **三级降级链**: CoinGecko→Binance→static 覆盖了 API 不可用的全部场景
3. **原子操作**: `deduct()` 为同步单一调用，无并发隐患
4. **死信不失**: 扣费失败进入死信队列而非静默丢弃
5. **可审计**: `reconcile()` + `verifyConservation()` 提供双重对账
6. **测试充足**: 6844 全量 0 fail + 135+ 积分专项测试

### 7.3 建议改进 (R105+)

| 优先级 | 建议 | 说明 |
|--------|------|------|
| P1 | 静态汇率自动更新 cron | 避免人工月度更新的遗漏 |
| P1 | Admin 死信恢复面板 | 支持人工审核+批量重新扣费 |
| P2 | 死信队列持久化到 SQLite | 目前为内存存储，进程重启丢失 |
| P2 | 对账 cron 定时执行 | reconcile() 目前需手动触发 |
| P3 | CoinGecko API Key 付费方案 | free API 有 RPS 限制 |
